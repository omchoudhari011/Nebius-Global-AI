Custodian · mobile app architecture

Custodian Frontend

The Custodian app is an Expo (React Native) app that runs on iOS, Android and the web. This page maps what is in the mobile/ code today (Step 1) and what each later step wires up. Every box and label comes from the repo.

  • Expo SDK 51
  • Expo Router 3.5
  • React Native 0.74
  • React 18.2
  • TypeScript (strict)
  • iOS · Android · Web

Dependency versions are the ones in package.json, which its README calls illustrative until npm install resolves them.

Sending a message, step by step

  1. 1

    You type in the TextInput and tap Send or press return. Both call onSend(); an empty message is ignored.

  2. 2

    onSend() clears the input and adds your message to messages, so it shows straight away.

  3. 3

    sendMessage(text) sends POST {API_BASE}/chat with the body {"message": text}.

  4. 4

    The backend answers {reply, used}. Today /chat replies echo: <your message> with an empty used; from Step 2 it runs orchestrator.handle().

  5. 5

    onSend() adds the reply to messages, keeping used on it for the provenance line (Step 2) and ContextRail (Step 5).

  6. 6

    ChatThread re-renders its FlatList: your bubbles on the right in the accent colour, replies on the left.

What each build step adds to the app

From the step notes in the code at the time.

  1. Step 1

    In the code now

    Chat screen, ChatThread, StatusPill, lib/api.ts, base colour tokens, a placeholder Tools & Data screen, and a tab bar joining the two. The backend's /chat echoes the message.

  2. Step 2

    Provenance

    ChatThread gets a tag line such as “used: Memory #12”. The backend's /chat calls orchestrator.handle(), which returns used as {memories, tools, skill}.

  3. Step 3

    Tools & Data

    The Tools & Data screen is built for real: Banner, and a PermissionRow per switch that calls setPermission() and then re-fetches getPermissions(). The backend gets its permission gate and sandbox.

  4. Step 4

    Sign-in and CORS

    The backend checks a signed session cookie on every route except /health (401 otherwise) and allows only the Expo web origin. The Nebius model backend is added.

  5. Step 5

    Active Context

    ContextRail shows the last reply's used: below the chat on screens under 700 px wide, beside it on wider ones. The backend gets the scheduler, skills and the notes tool.

  6. Step 6

    Dark mode

    lib/tokens.ts is filled in completely, including the dark variant.

Gaps still open

The first five affect the app as it is today; the rest come up while building Steps 3 to 5.

  1. The keyboard covers the message box on iOS. The input row sits at the bottom of the chat screen with no KeyboardAvoidingView, so the iOS keyboard slides over it while you type.
  2. Your own chat bubbles are hard to read. They use dark ink text on the accent purple: a contrast of 2.78:1, below the 4.5:1 readability minimum (WCAG AA). White text on the same purple is 6.25:1.
  3. Failed requests aren't handled. sendMessage() never checks res.ok, and onSend() has no try/catch, loading state or disabled Send button. A network error leaves your message with no reply, an error response (like the 401 coming in Step 4) shows an empty reply bubble, and tapping Send twice fires two requests.
  4. The chat doesn't follow new messages. The FlatList never scrolls to the end, so once the thread is taller than the screen, new messages land out of view.
  5. The safe area only works on iOS. Both screens use SafeAreaView from react-native, which does nothing on Android. The one from react-native-safe-area-context works on both.
  6. No scope is sent when you flip a switch. setPermission(toolId, granted) sends only {granted}, but the backend's grant() and revoke() take (user_id, tool_id, scope) and permissions are stored per scope. Calendar and notes each have read and write, so the request needs the scope too.
  7. Rows can't tell read from write. PermissionRow shows only tool_name, so a tool's read and write rows would look the same. Show scope on each row.
  8. tool_id has the wrong type. It's a string in the app's Permission type and setPermission(), but an INTEGER in the database and an int in permissions.py.
  9. The permission routes don't exist yet. backend/app/main.py has only /health and /chat, so both permission calls return 404 today.
  10. The web build won't send the session cookie. The fetch calls don't set credentials: "include", which the web build needs to send the Step 4 cookie to the API on another origin. Nothing issues that cookie yet either.
  11. used is untyped. It's Record<string, unknown> in the app, while the orchestrator's planned shape is {memories, tools, skill}. Typing it makes the Step 2 tag line and ContextRail safer to build.
  12. ContextRail can't sit beside the chat yet. Its wide layout sets a left margin and 180 px width, but the chat screen stacks its children in one column. It needs a row container on wide screens.
  13. The banner text will be nearly invisible. Banner sets opacity: 0.12 on its container, which fades the text too: a contrast of about 1.1:1. A translucent background colour keeps the text readable.
