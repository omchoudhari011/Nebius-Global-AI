Custodian Schema

The database behind Custodian, a single-user AI assistant. It remembers things about you, calls tools like your calendar or notes only with your permission, and runs scheduled jobs. This page shows the full diagram, which part of the backend saves each value, and every table explained column by column.

  • 15 tables
  • 83 columns
  • 21 relationships (20 foreign keys + 1 search-index link)
  • 5 groups
  • 4 encrypted columns

Most backend modules are still stubs (see docs/PLAN.md), so “saved by” names the module each write is assigned to in the plan.

How to read it

Colour = group

  • Identity 1 table
  • Access control 4 tables
  • Skills & scheduling 4 tables
  • Conversation 3 tables
  • Memory 3 tables

Line ends

  • Bar: exactly one row on that side
  • Circle + bar: zero or one (the link is optional)
  • Crow’s foot: many rows on that side

Example: a bar at the users end and a crow’s foot at the tasks end mean one user has many tasks.

Marks on columns

  • PKPrimary key: the column that identifies each row
  • FKForeign key: points to a row in another table
  • UQUnique: no two rows may share the value
  • Encrypted with Fernet before it is saved
  • plaintextStored readable, on purpose
  • Dashed border: virtual table (a search index)

Table tags

  • triggerWritten automatically by database triggers. App code never inserts here.
  • immutableA saved row can't be edited. A change is saved as a new version.
  • auditLogs every attempt, including the blocked ones.
  • FTS5SQLite full-text search index, stored as a virtual table.

Conventions

  • Timestamps are UTC text from datetime('now'), such as 2026-09-27 09:00:00, so they sort correctly as strings.
  • Encrypted columns are BLOBs holding Fernet ciphertext from app/crypto.py, keyed by APP_SECRET_KEY.
  • Foreign keys are enforced, because app/db.py turns them on for every connection.

SQLite fills every id and timestamp in every table, and Crypto encrypts the four columns just before they are saved, so neither has its own column in the grid.

Orchestratororchestrator.handle()

Runs Every chat message (mobile chat screen → POST /chat) and every scheduled task run, where it runs with no user message.

Saves

  • conversations: opens a chat thread when a new chat starts.
  • messages: your text, each model reply (with messages.skill_id, messages.model and messages.latency_ms) and one tool row per tool result. Text is encrypted first.
  • message_memories: one row per memory recalled for the reply it saves.
  • memories (through memory.write()): new facts it learns during a chat.

Reads

  • skills: picks one by keyword for each reply.
  • messages: the history sent to the model.
Model backendstub or Nebius Nemotron

Runs Whenever the orchestrator asks it for the next turn. The backend is set by MODEL_BACKEND and NEBIUS_MODEL_ID.

Saves

  • Nothing directly. Its reply text is saved by the orchestrator in messages, and each tool call it proposes is logged by the sandbox in tool_calls.

Reads

  • The conversation history from messages, passed in by the orchestrator.
Memory modulememory.write() · memory.recall()

Runs Called by the orchestrator during each chat, and by eval/memory_recall_eval.py to seed test memories.

Saves

  • memories: memory.write() saves the fact encrypted, with its memories.type, owner and optional expiry.
  • memories_fts: the plaintext search copy, in the same transaction. It is replaced when the text changes.

Reads

  • memory.recall() runs MATCH on memories_fts, then reads the matching memories rows for this user only, skipping expired ones.
Sandboxapp/tools/sandbox.py

Runs Once for every tool call the model proposes.

Saves

  • tool_calls: one row per proposed call, including blocked ones. It records tool_calls.status as the call passes each check, the encrypted tool_calls.args and tool_calls.result, tool_calls.error, tool_calls.latency_ms and tool_calls.finished_at.
  • The tool's result, which is saved as a tool row in messages.

Reads

  • tools: looks the tool up.
  • permissions: your switch, through permissions.check().
  • skill_tools: the current skill's allowed list.
Tool modulesapp/tools/

Runs When the sandbox runs them, using the runner named in tools.executor.

Saves

  • Nothing directly. Their output is encrypted into tool_calls.result and returned as a tool message.
Permissions modulepermissions.grant() · revoke() · check()

Runs When you flip a switch on the Tools & Data screen (POST /permissions/{toolId}), and right before every tool call.

Saves

  • permissions: grant() sets permissions.granted to 1 and revoke() sets it to 0, creating the row or updating it in place.
  • Each change is then copied to permission_events by a trigger, not by this module.

Reads

  • check() reads permissions. A missing row or granted = 0 means denied.
Schedulerapp/scheduler.py

Runs On startup, and at each task's cron time. Uses APScheduler.

Saves

  • task_runs: a running row when a task fires, updated to succeeded or failed with task_runs.error and task_runs.finished_at. On startup, leftover running rows are marked failed.
  • conversations: a task thread for each run.
  • tasks.next_run_at: the next run time, after each run.
  • Deletes expired rows from memories.

Reads

  • tasks: registers every active task on startup.
Cryptoapp/crypto.py

Runs Whenever another module saves private text. Fernet, keyed by APP_SECRET_KEY.

Saves

  • No rows of its own. It encrypts the four locked columns before they are saved: messages.content, tool_calls.args, tool_calls.result and memories.content.
Database triggersschema.sql

Runs Automatically, inside the database, when a matching row changes.

Saves

  • permissions_log_insert and permissions_log_update → permission_events, whenever a permission is created or its granted value changes.
  • memories_touch → memories.updated_at, when a memory's type, text or expiry changes.
  • memories_fts_delete → removes the memories_fts copy when a memory is deleted.
  • skills_immutable → blocks edits to a saved skills version.
SQLite defaultsbuilt into the database

Runs On every insert.

Saves

  • Every id (AUTOINCREMENT) and every created_at, started_at and changed_at (datetime('now')).
  • Column defaults: permissions.granted 0, tools.enabled 1, tools.executor sandbox, skills.active 1, tasks.status active, tasks.timezone UTC, conversations.channel chat, memories.type episodic.
schema.sql seedschema.sql

Runs Once, when the database is created from schema.sql.

Saves

  • tools: calendar and notes.
  • tool_scopes: read and write for each of them.
Developerby hand

Runs When a feature is added (Step 5 for skills).

Saves

  • skills and skill_tools: each new skill version and the tool scopes it may use.
  • tools and tool_scopes: a new tool module and its actions.
  • tools.category, and tools.enabled = 0 to switch a tool off.
Account setuponce

Runs Once, when the account is created.

Saves

  • users: the single account row.
Task setupyou, or the demo seed

Runs When you schedule a job (there is no API endpoint for this yet), or from the demo seed.

Saves

  • tasks: the job's name, skill version, schedule and time zone.
  • tasks.status: changed when you pause or resume.
Eval scriptseval/

Runs During testing, not in the running app.

Saves

  • eval/memory_recall_eval.py seeds test memories through memory.write().

Reads

  • eval/latency_eval.py reads messages.latency_ms and tool_calls.latency_ms.
  • tool_calls feeds the permission-block rate in eval/results.md.

The 15 tables

Each table opens with its full column list, as in the diagram, plus an example value for every column. Under it, every column is explained: what it stores, which part of the backend saves it and where the value comes from, and what it is used for.

About the example values. They are made up and follow one story: at 9:00 in Asia/Kolkata (03:30 UTC) on 27 September 2026, task 1 daily-summary fires as run 26, the assistant reads your calendar with list_events, and it uses memory 9, a saved preference. Encrypted values start with gAAAAAB, as every Fernet token does.

How data flows

The four ways data gets into the database, step by step, in the order they happen.

A chat message

Mobile chat screen → POST /chat → orchestrator.handle()

  1. Opens a conversations row with channel chat for a new thread, and saves your text in messages.
  2. memory.recall() searches memories_fts, reads the matching memories, and links them to the reply in message_memories.
  3. Picks a skill from skills by keyword and saves the model's turn in messages with that skill_id.
  4. For each tool the model proposes, the sandbox logs a tool_calls row, checks permissions and skill_tools, runs the tool, and saves the result as a tool message.
  5. Saves the final reply in messages, and writes any new facts to memories (encrypted) and memories_fts (search index).

InvolvesOrchestratorMemory moduleSandboxCrypto

A scheduled task

app/scheduler.py, at each task's cron time

  1. Inserts a task_runs row with status running.
  2. Opens a conversations row with channel task and runs the same orchestrator steps as a chat, with no user message.
  3. Marks the run succeeded or failed and writes the next time to tasks.next_run_at.

A permission switch

Tools & Data screen → POST /permissions/{toolId}

  1. permissions.grant() or revoke() creates or updates the permissions row.
  2. A trigger appends the change to permission_events.

  1. schema.sql seeds tools and tool_scopes; developers add skills and skill_tools; the users row is created at account setup.
  2. SQLite fills every id and created_at-style timestamp. Triggers keep permission_events, memories.updated_at and memories_fts deletes up to date.

What the design guarantees

  • Nothing is allowed by default. A tool call needs the tool enabled, your switch on in permissions and the skill's list in skill_tools, so scheduled jobs get only what their skill needs.
  • Full audit trail. Every tool attempt, including blocked ones, is in tool_calls, and every permission change is in permission_events.
  • Privacy. Message text, tool inputs and outputs, and memories are encrypted, and deleting a user removes all of their data, including the search copy in memories_fts.
  • Stable scheduled jobs. Skill versions can't be edited and tasks point at one exact version, so updating a prompt never silently changes a scheduled job.
  • Data integrity. Foreign keys are turned on for every connection in app/db.py, so every line in the diagram is a constraint the database checks. Every status-like column accepts only its listed values (CHECK), each task can have only one run in progress, and a tool message must answer exactly one tool call.
